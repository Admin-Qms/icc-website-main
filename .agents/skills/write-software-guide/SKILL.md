# Write an ICC software guide

Use the shared `keywordResearcher` through `node team/pm.js guide brief --next` or the Owner's assigned topic. Preserve the managed job ID and folder. `NOTHING_TO_GENERATE` is a stopping condition, not permission to invent another topic.

1. Read the job assignment and research queries. Search primary sources using available authorized web tools. Copy precise source URLs, attribution, retrieval dates and supported claims into a research fixture identifying the job. Keep URLs in `team/data/external-link-bank.json`. Do not edit that bank, capability facts or standards facts during a scheduled run. Missing evidence is a blocked research stage.
2. Prepare an enriched outline from the retrieved evidence. `guide outline --fixture <research.json>` uses the existing outline architect and saves a researched proposal; inspect it before checkpointing with `guide research --fixture <research-with-outline.json>`. A manually prepared research fixture may supply the same enriched outline contract. Read `guide.json`, `outline.json`, `research.json`, `state.json`, `guide-context.json` and `team/data/guide-writing-rules.md`. Each subsection needs evidence IDs, key points, workflow roles/inputs/decisions/records/exceptions and evaluation criteria. Only frozen final briefs authorize writing.
3. Write chapters sequentially from `chapter-briefs/<slug>.md`. Before each page, run `guide budget --job <id> --page <slug>`; aim near 2,000 words and stay within the reported allowance. The chapter policy permits up to 2,200 when the inclusive remaining budget fits. Use the exact assigned 3–5 H2 headings, no H1, useful internal links and relevant assigned evidence citations in each subsection. Read the shared context and earlier reviewed chapters; preserve terminology, the labeled hypothetical scenario and chapter boundaries. Use short paragraphs, actionable steps, useful tables and selective Important/Key Consideration callouts.
4. Checkpoint each page with `guide checkpoint --job <id> --page <slug>`, then run `guide review-chapter --job <id> --page <slug>` before proceeding. It reuses cleaner/grammar checks and requires scope, accuracy, citation, readability and repetition review. Inspect all findings. `guide revise --job <id> --page <slug>` applies at most two targeted subsection corrections while preserving citations and factual numbers. Otherwise make explicit targeted Markdown corrections, checkpoint and re-review. A failed, skipped or stale review blocks the next chapter. The reviewed summary updates shared context.
5. Write and review `introduction.md` after all nine chapters pass; target at least 1,500 words within its reported remaining budget. Match its promised coverage to the reviewed guide. The final chapter supplies 8–10 distinct substantive FAQ answers and closes with a software demonstration invitation linking `/contact/`. Read existing pages before correction; `guide resume --job <id>` identifies interrupted stages and invalidated checks.
6. Run `guide audit --job <id>` and inspect every finding. Required audits may not be skipped or self-certified. Missing credentials, stale reviews, incorrect claims or unresolved repetition block the guide. Run `guide publish --job <id> --dry-run`: it checks text first, then sources unique images and runs final checks without exposing published content. Finally run `guide validate --job <id>` to inspect the complete gate report.
7. Correct only the affected Markdown, at most two passes for a failed stage. Never change fixed metadata, source facts, checks, queues or rules to manufacture a pass. Preserve unresolved drafts and report the failed stage.

For editorial inspection of a complete draft, `guide preview --job <id> --port 3502` serves the real website renderer with tables, callouts, images, contents and chapter navigation. It is a long-running development server with a draft banner and noindex headers; stop it after inspection. It writes no public guide content. Image briefs supply managed heroes; do not emit unresolved image markers or untracked inline image links.

Use third person/direct address and US spelling. Hypothetical examples begin with `**Illustrative example:**`; no invented clients, features, quotations, statistics or results. ICC feature claims require verified ICC-specific evidence. Unverified capabilities are evaluation questions, not promises. Follow the supplied source's edition/scope; historical guidance does not establish today's edition.

Local publication through `guide publish` is distinct from a production push. Generate two complete guides per week; do not create a third topic for an already-completed slot. The routine's existing blog approval does not authorize guide commits, pushes or scheduling. Automatic guide release needs a separately documented Owner instruction.
